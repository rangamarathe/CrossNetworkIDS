The Generalization Gap

Building a network intrusion detector that scores 99.9999% accuracy is easy. Building one that still works on a network it wasn't trained on is not. This paper documents the full pipeline — and the eight-experiment investigation that followed when the first result turned out to be too good to be true.

Executive summary

A model that memorizes vs. a model that understands

We built a machine learning model to flag malicious network traffic ("is this connection an attack?") using a well-known security research dataset. On its own test data, the model was essentially perfect — it caught 100% of attacks while keeping false alarms low. That result was real, but it was also a trap: when we pointed the exact same model at a different network's traffic, performance collapsed. It started calling almost everything an attack, drowning out any real signal.

The rest of this paper is the investigation that followed. We measured exactly how much the two networks' traffic differed statistically, tried four different ways to patch the problem without collecting new data, watched three of them fail and one partially work, and eventually found that the real fix was the most obvious one: train on labeled examples from every network you actually care about, rather than hoping one model quietly generalizes to places it's never seen.

0.9999+ROC‑AUC on the model's own network — look flawless
0.807ROC‑AUC on a different network, same model, no retraining
50 / 84features with a severe statistical shift between the two networks
4 of 5quick fixes tried that failed to restore usable precision
0.88 / 0.75precision recovered once trained on both networks together
⚠ In plain terms

Imagine a security guard trained entirely at one office building. They get extremely good at spotting suspicious behavior in that building — but some of what they learned was really just "people here wear blue badges" and "the elevator dings twice," not genuine signs of trouble. Move that guard to a different building with red badges and a different elevator, and they either miss real threats or flag everyone at the door. That's exactly what happened here, and this paper is the story of figuring out which parts of what the guard learned were real security instinct, and which parts were just local trivia.

Section 1

The problem & the data

Every time two computers talk to each other over a network, that conversation can be summarized as a flow: who talked to whom, for how long, how much data went each way, how the connection was opened and closed, and dozens of timing and size statistics in between. A tool called CICFlowMeter converts raw network traffic into exactly this kind of summary — one row per conversation, roughly 85 numeric columns describing its shape.

We used two public research datasets built this way, both simulating a mix of normal office traffic and deliberately launched cyberattacks (port scans, denial-of-service floods, password-guessing attempts, botnets, and more) inside a lab network:

DatasetScaleCharacter
CICIDS2017 5 days, 2.1 million flows, ~1.1 GB One network, one week. Each weekday has a different attack type: Monday is attack-free, Tuesday is password-guessing, Wednesday is denial-of-service floods, Thursday is web attacks, Friday is botnets and scans.
CSE‑CIC‑IDS2018 10 captures across several weeks, ~63 million flows, ~30 GB A different, larger network, collected roughly a year later, with its own (related but not identical) menu of attacks.

Having two independently collected datasets of the same kind of data, from two different networks, turned out to be the single most important thing about this project — it's what let us catch the generalization problem at all, instead of shipping a model that looked perfect and quietly failed in the field.

Section 2

Building the pipeline

Before touching any model, we defined the actual decision this system is meant to change: a security analyst's queue. The model's job isn't to "detect hackers" in the abstract — it's to look at a network flow and decide whether a human analyst should be pulled in to review it. That framing set the success criteria for everything after it: missing a real attack (a false negative) is far more costly than an analyst spending a minute clearing a false alarm, so the project targets high recall (catch nearly everything) subject to a precision floor (don't flood the queue with false alarms) — not raw accuracy, which is a misleading target when only about a quarter of the traffic is actually an attack.

Concretely, for each stage:

  • Clean & label. Removed exact duplicate rows, capped a handful of extreme outlier values, and derived the target: is_attack (yes/no) plus a diagnostic attack_family label for later analysis. Columns that would let the model "cheat" — IP addresses, flow identifiers, timestamps, and a column that nearly encodes the answer directly — were removed before training.
  • Split. Data was divided 64% training / 16% validation / 20% test, keeping the proportion of attacks consistent across each portion (a stratified split). The test portion is never looked at until the very end, to keep the final score honest.
  • Preprocess. Missing values filled with the column median; numeric columns rescaled to a common range; the one categorical column (network protocol) one-hot encoded. Critically, this rescaling is learned only from the training data and then applied unchanged to validation and test data — the same discipline used on any new data at prediction time.
  • Train. Four candidate models were compared: a "dummy" baseline that always guesses the majority class (the floor any real model must beat), logistic regression, a random forest, and a gradient-boosted tree ensemble.
  • Evaluate. The winning model is scored exactly once on the held-out test set, plus a bootstrap confidence interval and a breakdown by day and by attack type, so a single lucky number doesn't stand in for the whole picture.
Section 3

A suspiciously perfect result

The random forest won the model comparison by a wide margin, and its result on CICIDS2017's own locked test set was, on paper, about as good as a security detector can look:

MetricScorePlain-language meaning
ROC‑AUC0.999999Ranks attacks above normal traffic essentially every single time
Recall1.000Caught 100% of the real attacks in the test set
Precision0.85085% of its alerts were genuine attacks

A result this clean should make anyone suspicious, and it made us suspicious. We checked which features the model actually relied on (no single "cheat" column dominated its decisions — the signal was spread across roughly fifteen legitimate traffic statistics), which ruled out the most obvious kind of bug. But two more subtle, well-documented properties of this exact benchmark were still in play: attack-generating tools tend to fire bursts of near-identical traffic within seconds of each other, so some of the "different" flows in the test set are really faint echoes of ones the model already memorized in training; and the attacks in this dataset are simply generated by tools whose traffic looks statistically very different from ordinary office traffic, which is a property of this lab environment more than of real-world attackers.

⚠ In plain terms

A student who scores 100% on every practice test using the exact same textbook might genuinely understand the material — or might have simply memorized the answer key. The only way to tell the difference is to give them a different exam covering the same subject. That's exactly the test we ran next.

Section 4

Testing on a different network

We took the CICIDS2017-trained model, changed nothing about it, and pointed it at a 2.45-million-flow sample drawn from all ten CSE-CIC-IDS2018 capture files — a network the model had never seen a single row of.

TestROC‑AUCRecallPrecision
Its own network (CICIDS2017)0.99999941.0000.850
A different network (CSE‑CIC‑IDS2018)0.8070.9280.119

Recall barely moved — the model still caught most real attacks. Precision, though, collapsed from 0.85 to 0.12: roughly 7 out of every 8 alerts on the new network would have been false alarms. For a security team, that's the difference between a useful tool and one everyone learns to ignore within a week.

We then ran the mirror-image experiment for a fuller picture: training on a representative 2.45-million-row sample of CSE-CIC-IDS2018 (drawn from a full scan of all ten files, not just the first few, so rare attack traffic buried later in a capture isn't missed) and testing on the complete, untouched CICIDS2017 dataset.

DirectionROC‑AUCRecallPrecision
Train 2017 → test 20180.8070.9280.119
Train 2018 → test 20170.9400.9940.363

The gap is real in both directions, but it's asymmetric: a model trained on the larger, more varied CSE-CIC-IDS2018 capture (ten different days across several weeks) transferred to CICIDS2017 far better than the reverse. Since ROC-AUC doesn't depend on wherever you set the alert threshold, this is a genuine difference in how well each model learned to rank traffic by how attack-like it looks — not just a knob that needed adjusting.

⚠ In plain terms

Train a guard at one single office for one week, and they'll pick up on a lot of quirks specific to that one place. Train a guard by rotating them through ten different sites over several weeks, and they're forced to learn what "suspicious" actually looks like in general, because no single site's quirks work everywhere. That's the practical reason the broader dataset produced a more portable model.

Section 5

Diagnosing why: measuring "drift"

To find out why performance falls apart, we measured how much each of the model's input measurements differs between the two networks, using a standard statistic called the Population Stability Index (PSI). In plain terms: for one feature at a time, take the range of values seen in the training network, and check how much of that same range the new network's values actually land in. If the two networks' traffic looks statistically similar for that measurement, PSI is close to zero. The more the shape of the distribution has shifted, the higher PSI climbs — and by convention, anything above 0.2 is considered a meaningful, investigate-worthy shift.

FeaturePSI (2017 → 2018)What it measures
Fwd IAT Max1.98Longest gap between packets sent forward
Fwd IAT Total1.95Total time between forward packets
Bwd Packet Length Max1.88Largest packet sent back to the initiator
FWD Init Win Bytes1.61Initial TCP window size the connection advertised
RST Flag Count0.02How often a connection was abruptly reset

Overall, 50 of the model's 84 input features showed severe drift (PSI > 0.2) between the two networks. But drift alone doesn't explain a performance collapse — a feature the model barely uses can drift wildly without consequence. What matters is whether a drifted feature is also one the model actually relies on. Cross-referencing drift against the random forest's own feature-importance ranking told a more precise story:

FeatureImportance to the modelDrift (PSI)Risk
RST Flag Count10.4%0.02stable & trusted
FWD Init Win Bytes5.9%1.61unstable & trusted
SYN Flag Count5.0%0.15mild drift
ACK Flag Count3.3%0.45unstable & trusted

The model's single most-trusted signal, RST Flag Count, turned out to be nearly identical between the two networks — which is part of why the model still caught most attacks abroad (recall stayed high). But its second-most-trusted signal, the TCP window size, was wildly different: a closer look showed CICIDS2017's typical value clustering around 29,200 (a common Windows default) while CSE-CIC-IDS2018 clustered around 8,192 (a common Linux default). The model had partly learned "a window size near 29,200 looks attack-adjacent," which is really just "this looks like the operating system this lab happened to use," not a property of attacks at all.

⚠ In plain terms

PSI is a "how different does this measurement look between two places" gauge, not a verdict on the model. The real risk shows up only when you combine it with "and does the model actually care about this measurement?" — the equivalent of a guard who learned to pay close attention to the color of employee badges, which happened to be reliably blue at one office and are, for entirely unrelated reasons, red at the next.

Section 6

Four attempted fixes — and how each one fared

Rather than immediately jumping to "collect more data" or "give up," we tried four increasingly sophisticated ways to patch the generalization gap without any new labeled data from the target network, evaluating each one the same way: same frozen or newly trained model, judged on precision against the CSE-CIC-IDS2018 sample.

Attempt 1 — drop the most unstable features

The most intuitive idea: if a feature's distribution is unreliable across networks, stop using it. We tried dropping all 50 high-drift features, and separately, dropping only the ones that were both high-drift and important to the model.

Feature setCross-network ROC‑AUCRecallVerdict
All 84 features (baseline)0.8070.928—
Drop all 50 high-drift features0.7210.608✗ worse
Drop only high-drift + important ones0.7540.771✗ worse

This made things worse, not better. A drifted feature is not automatically a useless one — random forests draw much of their robustness from having many overlapping, partially-redundant signals, and removing three dozen of them threw away real predictive information along with the instability.

Attempt 2 — translate the new network's numbers into the old network's scale

A more surgical idea: instead of deleting unstable features, translate each value. For every flow in the new network, we found where that value ranked within that network's own traffic (its percentile), then substituted whatever value sits at that same percentile in the original network's traffic. In effect: "this flow's window size is unusually large for its own network — here's the equivalent unusually-large value back home."

VersionROC‑AUCRecallPrecision
Raw values (no translation)0.8070.9280.119
Translated values0.8841.0000.073

A genuinely mixed result. The translation worked exactly as designed for smooth, continuous measurements — timing-related drift dropped from severe (PSI 1.87) to negligible (PSI 0.03). Raw ranking quality (ROC-AUC) improved too. But precision at any practical alert threshold got worse. Fixing each measurement in isolation disturbed the combinations of measurements the model's decision rules actually depend on — like correcting every word in a sentence individually and ending up with a sentence that no longer parses.

Attempt 3 — retrain from scratch in a "universal" measurement space

A more principled version of the same idea: instead of translating one network's values into the other's units, convert both networks' measurements into a shared, unitless space — "how unusual is this, relative to its own network" — and train the model on that from the start, so it never sees an absolute value like "8,192" at all.

VersionROC‑AUCPrecisionVerdict
Attempt 2 (value translation)0.8840.073—
Attempt 3 (universal rank space)0.8520.072✗ no better

The theoretically cleaner approach did not win — it scored slightly below the simpler translation trick, and had the worst precision of anything tried up to this point. The most likely reason: compressing every measurement down to "just its rank" throws away information about how tightly values cluster, which the model was also relying on.

Attempt 4 — leave the model alone, fix the alarm threshold

Every attempt above reused the alert threshold chosen on CICIDS2017's own data — a very low bar, since the model's scores there are cleanly separated into "clearly benign" and "clearly attack." On a different network with a different score distribution, that same low bar meant flagging almost everything. We tried something much simpler: keep the original model completely untouched, and just re-pick the alert threshold using a small labeled sample from the new network.

ThresholdValueRecallPrecision
Old (tuned on the original network)0.00020.9290.119
New (tuned on the new network)0.9800.0970.921

This is the best result among every frozen-model fix tried — precision jumped from 0.12 to 0.92, with zero retraining and zero feature engineering. The catch: at that precision level, you only catch about 1 in 10 real attacks. Section 7

What actually worked: train on both networks

Every fix so far tried to patch a model that only ever saw one network's labeled traffic. The last experiment asked a more basic question: what if it simply saw both? We trained one random forest on the combined training portions of CICIDS2017 and CSE-CIC-IDS2018, then evaluated it on a held-out test slice of each network separately.

Evaluated onROC‑AUCRecallPrecision
Held-out CICIDS20171.0001.0000.881
Held-out CSE‑CIC‑IDS20181.0001.0000.752
Both, combined1.0001.0000.848

This clears the precision guardrail on CICIDS2017 outright and comes close on CSE-CIC-IDS2018 — both at perfect recall, and comprehensively ahead of every cross-network number and every correction trick tried above.

⚠ Important caveat

This is not the same kind of test as the earlier cross-network checks. This model did see CSE-CIC-IDS2018 traffic during training — just not these specific held-out rows — so its strong showing there is more like "a student who studied from both textbooks acing an exam drawn from both," not "a student who studied from one textbook and aced a completely different one." What this experiment actually demonstrates is narrower, but still practically the most useful finding in this paper: if you have labeled data from every network you plan to deploy to, one combined model can serve all of them well — you don't need a separate model per network. It says nothing about a genuinely new, still-unseen network, which would still need its own labeled data folded in.

Section 9

Lessons learned

  1. A near-perfect score is a prompt to investigate, not a finish line. ROC-AUC of 0.999999 wasn't a bug — it was a symptom. The fix wasn't to distrust the number, it was to test the model somewhere the number couldn't reach: a second, independently collected dataset.
  2. Recall and precision can move in opposite directions, and only one of them is usually in trouble. Throughout this investigation, recall stayed reasonably high almost everywhere; precision is what collapsed. A dashboard that only reports one combined "accuracy" number would have hidden this entirely.
  3. Statistical drift explains a mechanism, not a verdict. Fifty drifted features sounds alarming, but only the ones the model actually leans on turned out to matter. Measuring "different" and measuring "harmful" are two separate questions.
  4. The theoretically cleaner fix isn't automatically the better one. Retraining on a "universal" measurement space sounded more principled than simple value translation, and it performed worse. Empirically testing a hypothesis beats reasoning about it from first principles.
  5. Check the cheap fix before the expensive one. Recalibrating a single number (the alert threshold) using existing model outputs got closer to a usable result than three separate feature-engineering efforts combined.
  6. The most reliable fix for "this doesn't work somewhere new" is data from that somewhere, not a cleverer algorithm. No amount of correcting a frozen model matched simply including labeled examples from the target network in training.
Section 10

Limitations & next steps

  • No true third-network test exists. Every "generalization" claim in this paper is bounded by having exactly two datasets. Whether the combined model would work on a genuinely new, unseen network is still an open question.
  • Hyperparameter tuning was not performed. All models used reasonable default settings rather than a systematic search; a tuned model might shift these numbers somewhat.
  • No SHAP or per-decision explanation report has been produced. Feature importance here is global (which features matter overall), not local (why did the model flag this specific flow).
  • Rare attack categories remain a blind spot. Several attack types have fewer than 20 examples in the entire CICIDS2017 dataset (Heartbleed: 11 rows); reported perfect recall on those categories reflects a very small sample, not a strong guarantee.
  • This dataset reflects lab-generated attack traffic from 2017–2018. Real attacker behavior evolves; any production use would need an explicit retraining policy, not a one-time model.
Glossary

Terms used in this paper

Network flow
One summarized conversation between two computers — who talked to whom, for how long, and dozens of statistics about the traffic in between. The unit of data this whole project works on.
Recall
Of all the real attacks that happened, what fraction did the model catch? Missing an attack (a false negative) hurts recall.
Precision
Of all the alerts the model raised, what fraction were real attacks? A flood of false alarms (false positives) hurts precision.
ROC‑AUC
The probability that a randomly picked attack scores higher than a randomly picked normal flow. 0.5 is a coin flip; 1.0 is perfect ranking. Doesn't depend on where you set the alert threshold.
PR‑AUC
Similar to ROC-AUC, but built from precision and recall instead — more informative than ROC-AUC when attacks are rare, which is the normal case here.
Population Stability Index (PSI)
A single number measuring how much a feature's distribution has shifted between two datasets. Below 0.1: no meaningful change. Above 0.2: investigate.
Threshold
The cutoff score above which a flow gets flagged as an attack. Lower thresholds catch more attacks but raise more false alarms.
Feature drift / data drift
When the real-world inputs a model sees start to look statistically different from what it was trained on — a different network, a different time period, a different customer base.
Cross-dataset / out-of-distribution test
Evaluating a model on data it never saw a single example of during training, as opposed to a held-out slice of the same collection it was trained from.
